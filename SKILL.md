# Новый проект

Скилл разворачивает **скелет, а не продукт**: папки, конфиги, правила, линт,
документацию, ключи сервисов и рабочую аутентификацию. Дальше фичи пишутся по
этим правилам.

## Запреты на весь прогон

- **Никакой своей логики.** Нет функций-заглушек, «примерных» экранов,
  фейковых данных, `TODO`-реализаций, демо-компонентов.
- Пустая папка держится своим `AGENTS.md` (+ `CLAUDE.md` с `@AGENTS.md`), если
  у неё есть правила, иначе `.gitkeep`.
- Исключения по решению владельца:
  - аутентификация работает по-настоящему;
  - интеграции получают полупустую папку: `AGENTS.md`, ключи в
    `.env.example` и `env.ts` (optional), зависимость установлена, кода нет;
  - будущие покупки получают пустой класс `PurchasesService` без методов.
- **Версии не из памяти.**
  - Официальные генераторы (`create-next-app@latest`) и `npm i <pkg>@latest`.
  - Версии, которые поставил генератор (eslint, typescript, tailwind),
    главнее «@latest»: их не поднимают вручную. TypeScript в репозитории один.
  - Перед кодом на библиотеке читать доки установленной версии. Для Next это
    `node_modules/next/dist/docs/`, у Better Auth и других пакетов их docs.
  - Для Gradle, SPM и CocoaPods брать последнюю стабильную версию с Maven
    Central и GitHub releases.
- **Секреты.**
  - Ключи не печатаются, не пишутся в файлы репозитория и не спрашиваются в
    чате. Владелец кладёт их в файлы сам (`reference/services-direnv.md`).
  - `direnv allow` запускает владелец.
- **Ничего наружу без явной просьбы:** ни коммита, ни пуша, ни создания
  репозитория на GitHub, ни деплоя, ни изменения проектов в Railway, Vercel,
  Stripe, Firebase. Проверки сервисов и репозитория только на чтение.
- **Локально бэк и веб запускаются через `npm run dev`**, как обычные процессы
  (`tsx watch` и `next dev`), а не контейнерами. Dockerfile для API не
  создаётся, в проде Railway собирает его сам (Railpack). Docker локально не
  нужен вовсе: Postgres берётся из brew (`brew services`), как в clan-front.
- **Место на диске и память.** Сборки iOS (Firebase SDK) и Android (Gradle,
  Kotlin) съедают гигабайты DerivedData, кэшей и swap.
  - Перед каждым `npm install`, `next build` и `npm run dev` проверять
    `df -h ~`: меньше 6 ГБ свободно, значит стоп, сказать владельцу.
  - Перед сборками iOS и Android (фазы 6, 7, 11 и `gradle wrapper`): меньше
    20 ГБ, значит не собирать. Сказать владельцу, сколько свободно и что можно
    почистить, записать в init-задачу.
  - Gradle запускать с `--no-daemon` и
    `-Pkotlin.compiler.execution.strategy=in-process`, чтобы после проверки не
    висели демоны.
  - Сборки платформ идут по очереди, не параллельно.
- **Язык.** Код, идентификаторы, тексты интерфейса и сообщения коммитов на
  английском. Комментарии «почему», `AGENTS.md` и вся документация на русском,
  без длинных тире в тексте для людей. Исключение: блок правил Next в
  `AGENTS.md` дословный, его пишет и восстанавливает `next dev`.
- **Плейсхолдеры в `templates/`.**
  - Формат только `{{UPPER_SNAKE}}`, все значения в `reference/placeholders.md`.
    После копирования не остаётся ни одного; неизвестное значение становится
    пустой строкой и пунктом «что сделать руками».
- **Маркеры частей в `templates/`.** Части: `web`, `ios`, `android`,
  `railway`, `firebase`, `stripe`, `vercel`, `apple`, `posthog`,
  `google-sign-in`, `admin`. Нет части: помеченное удаляется. Есть: удаляется
  только маркер. Применяет их и плейсхолдеры скрипт
  `templates/apply.mjs <values.json> <шаблон> <файл>` (проверен полным
  прогоном); руками маркеры не вычищаются.
  - `# [x]` на своей строке в yml, shell, gitignore: идущие следом строки
    комментария, следующая строка и всё, что под ней с большим отступом.
  - `// --- [x] Название ---` и `# --- [x] Название ---`: секция до следующего
    заголовка вида `--- … ---`, любого, в том числе без маркера. Если часть
    есть, из заголовка удаляется только `[x] `, название остаётся.
  - `<!-- [x] -->` в конце строки md: эта строка или пункт списка целиком
    вместе со строками продолжения.
  - `<!-- [x] -->` на своей строке: следующий блок (заголовок вместе с его
    разделом, абзац или блок кода).
- **После каждой порции кода `npx eslint --fix .`**: `import/order`
  расставляет импорты сам, без этого почти каждый новый файл падает на линте.
- **npm workspaces.** Новый пакет: сначала `npm install` в корне, потом
  `npm i <pkg> -w <workspace>`. Каждый раз проверять, что зависимость попала в
  `package.json` пакета: первая установка в свежий workspace бывает только
  ссылкой.

## Порядок

### 0. Вопросы: одним списком, текстом

Не через инструмент вопросов, а нумерованным списком в сообщении, с
рекомендацией у каждого пункта. Очевидное выносится в «беру по умолчанию,
если не возразите». Спросить:

1. Название проекта (для `Documentation [Name]`), slug, домен, bundle id iOS и
   applicationId Android.
2. **Git:**
   - в какой репозиторий добавить: URL существующего или «создать новый»
     (создание на GitHub только после явного «да»);
   - под каким аккаунтом GitHub;
   - основная ветка (по умолчанию `main`) и вторая (по умолчанию `dev`).
3. Основа: **веб** или **приложение**. Какие платформы делаем сейчас: веб, iOS,
   Android.
4. Бэкенд: **Railway** (Fastify + Drizzle + Postgres, аутентификация Better
   Auth) или **Firebase** (Functions + Firestore + Firebase Auth).
5. Какие зоны веба нужны: `(www)` лендинг, `(app)` приложение, `(admin)`
   админка. Один домен или поддомены `www.` / `app.`.
6. Способы входа: email + пароль, Google, Apple. Если есть Google и iOS, нужен
   и Sign in with Apple (App Store 4.8). Railway: почта для писем
   подтверждения и сброса пароля, какой сервис или позже (если позже, сброс
   пароля недоступен до её подключения, это пишется в init-задачу). Firebase:
   письма шлёт сам Firebase Auth, вопрос про почту не задаётся.
7. Внешние сервисы: Stripe, Apple, PostHog, Railway, Vercel, Firebase.
   - Для каждого: аккаунт (имя файла токена; у Stripe имя профиля CLI).
   - **PostHog сразу предложить отложить.** Если отложили, делаем пустую
     `services/analytics/` без ключей и SDK.
8. Будут ли покупки в будущем. Если да, делаем пустые заготовки
   (`reference/layout.md`).

По умолчанию: iOS 17+, Android minSdk 26, потолок 500 строк кода на файл.
Railway: Postgres из brew на `localhost:5432` (общий сервер, базы проекта с
префиксом slug). Firebase: эмуляторы на проекте `demo-<slug>`.

### 0.5. Доступы: все сразу, одним списком

Сразу после ответов, до любого кода, **одним сообщением** перечислить всё, что
нужно для доступов к выбранным сервисам и репозиторию. Состав по сервисам:
таблица «Доступы на старте» в `reference/services-direnv.md`. Для каждого пункта:

- **секрет** (токен, ключ `.p8`, service account): куда владелец кладёт файл
  сам, с готовой командой. В чат секреты не присылаются;
- **идентификатор** (ID проекта, Team ID, Key ID, client ID): владелец
  называет в чате, это не секрет;
- **файл из консоли** (`GoogleService-Info.plist`, `google-services.json`):
  откуда скачать и куда положить;
- **действие в консоли** (включить провайдер входа, создать OAuth client):
  что именно сделать.

Дождаться «готово» (можно частично). Проверка идёт в фазе 1, как только в
папке появится `.envrc`.

### 0.7. Полный план: подтвердить в чате

После ответов и «готово» по доступам, до git и любого кода, **одним
сообщением** показать полный план со всеми деталями:

- все ответы на вопросы фазы 0 и значения, взятые по умолчанию;
- доступы: что получено, что отложено или ещё не сделано;
- стек и структура: платформы, бэкенд, зоны веба, способы входа, сервисы,
  заготовки (покупки, пустой `analytics/`);
- git: репозиторий, аккаунт, ветки, создаётся ли репозиторий на GitHub;
- фазы 1–13 по порядку, что в каждой делается под этот проект;
- что владелец делает руками и что откладывается.

Ждать явного «да». Правки вносятся в план, и он показывается заново
целиком. После «да» идём по всем фазам до конца без новых остановок; явное
«да» отдельно нужно только там, где его требует этот скилл (создание
репозитория, коммит, пуш, удаление задачи).

### 1. Git и первая задача в доках: сразу после доступов

Перед любым другим кодом всегда git:

1. `git init -b <основная ветка>`. Вторая ветка создаётся после первого
   коммита (фаза 12, коммит только по просьбе): в репозитории без коммитов
   `git branch` падает. Если в remote уже есть история: `git fetch origin` и
   основная ветка от `origin/<основная>`.
2. Локальная личность для выбранного аккаунта только в этом репозитории:
   `git config user.name` / `user.email`. Глобальный конфиг не трогать.
3. `git remote add origin <URL>`. Репозитория нет и владелец сказал
   «создать»: `gh repo create` (приватный) только после явного «да». Пуш
   только по просьбе.
4. `.envrc` из `templates/root/.envrc.tpl` с блоками выбранных сервисов и ID
   из ответов. Попросить владельца выполнить `direnv allow`.
5. **Проверка доступов одним проходом на чтение:** direnv-доступы через
   `direnv exec . <команда>`, консольные по таблице
   (`reference/services-direnv.md`), включая `git ls-remote origin` (нет `gh`:
   так и записать, `git ls-remote` для доступа достаточно).
   Результат владельцу таблицей «доступ / ок / нет + причина». Чего нет,
   уходит в «что сделать руками» init-задачи. Скелет строится дальше и не
   ждёт, обходных путей нет.
6. Каркас `Documentation [Name]/`: `CLAUDE.md` из `templates/docs/`, папки
   `architecture/`, `db-scheme/` (для Railway), `tasks/{blocking,bugs,additions}/`.
7. `tasks/blocking/project-init.md` из `templates/docs/project-init.md`. В неё
   записать все ответы, решения, таблицу доступов, «что сделать руками» и план
   по фазам ровно в том виде, в каком его подтвердили в фазе 0.7. Это «да»
   и есть согласие владельца на эту задачу.
8. Каждая следующая фаза отмечается в задаче сразу по завершении. Находки,
   меняющие план (конфликт версий, отложенный шаг), идут в «Что выяснилось по
   дороге» с датой.

### 11. Приёмка

1. `/gate` проекта (`templates/claude/skills/gate/SKILL.md`, шаги платформ,
   которых нет, удалены) зелёный целиком.
2. Railway:
   - `npm run dev` поднимает базу ветки, API и веб;
   - `curl /health` отвечает 200;
   - регистрация, вход, `get-session` (кукой и bearer), выход и удаление по
     email работают через `curl` на API и через `/api` веба. Запросы с кукой
     шлются с `-H 'Origin: <адрес веба>'`, иначе Better Auth отвечает 403;
   - `npm run dev-session` выдаёт рабочие куку и bearer;
   - на вебе вход проверен в превью. Превью читает `.claude/launch.json` из
     рабочей папки сессии; если сессия открыта не в корне проекта, запустить
     `npm run dev` в фоне и открыть превью по адресу;
   - `npm run db:fork-check` и `npm run db:branches` отвечают без ошибок.
3. Firebase:
   - `npm run dev:firebase` поднимает эмуляторы на `demo-<slug>`;
   - через REST эмулятора Auth работают регистрация, вход, неверный пароль
     даёт ошибку, удаление аккаунта;
   - Firestore отвечает 403 (правила закрыты).
4. iOS собирается под симулятор, Android `assembleDebug` проходит. Если на
   машине нет Xcode или Android SDK, это пишется в init-задачу, а не
   замалчивается.
5. Плейсхолдеров не осталось: `grep -rn '{{[A-Z_]*}}'` по проекту пустой.
6. Отчёт владельцу: таблица «проверка / результат», провалы с выводом.

### 12. Закрытие

- Решения из init-задачи переносятся в заметки `architecture/`.
- Удаление задачи и первый коммит ждут фазы 13: сначала сверка, потом
  вопрос владельцу.
- Спросить владельца, удалить ли задачу. Удалять только после «да», вместе со
  строкой реестра.
- Предложить первый коммит, делать его только по просьбе. Сообщение на
  английском. После первого коммита создать вторую ветку (`git branch dev`);
  пуш тоже только по просьбе.
- С этого момента в проекте действует правило «доки и задачи только в
  основной ветке»: правка `Documentation [Name]/` и реестра задач коммитится
  в основную ветку и сразу подтягивается во все остальные (раздел в корневом
  `AGENTS.md`). Сказать об этом владельцу в отчёте.
- Отдельно перечислить, что осталось сделать руками (из init-задачи).

### 13. Сверка со скиллом

Последняя фаза, отдельно от приёмки: приёмка проверяет, что проект работает,
сверка проверяет, что сделано всё, что требует скилл.

1. Заново прочитать этот `SKILL.md` и все reference-файлы выбранных частей.
   По памяти не сверять.
2. Пройти каждый пункт: фазы 0–12, «Запреты на весь прогон», подтверждённый
   в фазе 0.7 план и init-задачу. Для каждого пункта проверить факт в
   репозитории (файл, команда, вывод), а не отметку в задаче.
3. Пункты, которые не относятся к выбранной конфигурации (нет Android, нет
   Railway и т. п.), помечаются «не применимо» с причиной.
4. Что не закрыто, доделать сразу и повторить `/gate`. Что доделать нельзя
   (нет доступа, нет Xcode/SDK, отложено владельцем), записать в «что
   сделать руками» с причиной.
5. Отчёт владельцу таблицей «пункт скилла / где проверено / ок, доделано,
   не применимо, нет + причина». Только после этого вопрос об удалении
   init-задачи и предложение первого коммита из фазы 12.
